# Tier 2 kernels and acceptance queries on x86: measurements

This document measures the tier 2 kernels against native Rust loops at 10M rows, and times the seven acceptance queries against corgi and DuckDB on one thread.
The tier 2 spec sets no speed target, so the tables record how far each kernel and query is from the references and which primitives are strain cases.
Kernels that lost to the compiler's output, or whose assembly shows a scalar loop, are listed as strain cases with the measurement behind each decision.
Every number comes from the x86 host described below, and an aarch64 section follows from the M5 session.
The final section names the first gap to close in plan 5.

The reported acceptance run started at load 4.71 and ended at 3.90, and its corgi run started at 3.90 and ended at 3.74.
Differences of a few percent between runs are noise.

## How the systems were timed

* Verkehrt kernels: criterion with `sample_size(10)`, a 0.5 s warm-up, and a 3 s measurement time (`benches/tier1.rs`, groups `tier2/*`). Tables give the criterion mean. Throughput counts input bytes read (8 bytes per row per array input, 1 byte per bool row), in decimal GB/s.
* Verkehrt acceptance queries: the same criterion settings (`benches/acceptance.rs`), one group per query and variant, timing `execute` only. Parsing, planning, and loading the column files happen before the timed region. Tables give the criterion mean.
* corgi: the best of at least 3 runs (up to 50 within 1.5 s) of `Program::run`, with the input `Value` cloned per run and outside compile and load. Corgi's filter matches by substring, so the `q01` filter also ran TPC-H `q01b`.
* DuckDB: the best of repeated runs with the table in memory and `SET threads = 1`, read from `duckdb.tsv`.
* Variants: `scalar` is the portable entry on the baseline target, `avx2-auto` and `avx512-auto` compile the same body under the ISA's target features, and `-intrinsics` is the default backend, which uses a hand-written entry where one exists and the `auto` entry otherwise.

Criterion's mean is slower than a best-of time by a few percent, so the corgi and DuckDB columns favor those systems slightly against Verkehrt.
The results file also records the fastest criterion sample per bench.
The reference streaming kernel, `add` on `i64`, reads 160 MB in 9.17 ms (avx2-auto), which is 17.44 GB/s, against 7.08 ms for the native loop.
The 1.3x between them is interpreter overhead, most likely the zeroed output buffer that `Array::try_zeroed` writes before the kernel writes it again, though this attribution was not measured separately.

### A bug the measurements found

At commit 9bb5e11 the `auto` entry of every whole kernel (`gather`, `histogram`, `reduce_into`, `argsort`) was a 14-byte stub that called the baseline build of the kernel body, so these entries ran the scalar code on every ISA.
The first run showed it as auto-over-scalar ratios near 1.0, which looked like a body that does not vectorize, and the disassembly showed the stub.
Commit 2ffb751 marks the four bodies and their helpers `#[inline(always)]`, and the entries are now 1.5 to 2.2 KB with the ISA's vector code.
No test guards against a regression, because checking that an entry contains vector code needs a disassembler, so the same bug could recur silently.
The tables below are from after the fix, and the run before it is listed in the results file for the comparison.

### Assembly verdicts

The verdicts come from `objdump -d` of the bench binary, because timing alone cannot tell a vectorized loop from a scalar one in these memory-bound kernels.

| Kernel | AVX2 hot loop | AVX-512 hot loop | Verdict |
|---|---|---|---|
| `scan` add i64 | scalar `add`, 4 rows per iteration, no vector registers | same | Scalar loop on both ISAs |
| `scan_by` add i64, auto | branch-free scalar loop, one row per iteration (`cmp byte`, `cmovne`, `add`) | same | Scalar loop, a `cmov` plus `add` dependency per row |
| `scan_by` add i64, intrinsics | none | `zmm`, 8 rows per iteration, `vptestmb` on the start bytes, three `valignq` plus masked `vpaddq` steps, `vpermq` carry broadcast | Vectorized on AVX-512 only |
| `prev` i64 | `copy_from_slice`, a call to libc `memcpy` | same | Vectorized by libc, not by the entry |
| `gather` i64, auto | bounds pass on `ymm`, scalar row loop | bounds pass on `zmm`, scalar row loop | Bounds pass vectorized, gather scalar |
| `gather` i64, intrinsics | row loop `vpgatherqq ymm`, 8 rows per iteration | row loop `vpgatherqq zmm`, 16 rows per iteration | Vectorized |
| `histogram` | bounds pass on `ymm`, scalar `inc` per key | bounds pass on `zmm`, scalar `inc` per key | Bounds pass vectorized, bucket loop scalar |
| `reduce_into` add i64 | as `histogram`, scalar `add` per row | same | Bounds pass vectorized, bucket loop scalar |
| `div_const` i64, u64 | `ymm` shifts, 4 scalar `mul` per iteration for the multiply-high | `zmm` shifts, 8 scalar `mul` | Partially vectorized, multiply-high scalar |
| `and`, `xor`, `not`, `add` i64 | `ymm`, 16 rows per iteration | `zmm`, 32 rows per iteration | Vectorized, and the baseline build is SSE2-vectorized too |
| `argsort` i64 | index initialization on `ymm`, then baseline `ipnsort` | same on `zmm` | Scalar sort |

Timing and assembly disagree in two places, and the assembly decides.
`histogram` and `reduce_into` time at 0.79 and 0.85 of scalar, but the bucket loop is scalar, so the gain is the bounds pass moving from SSE2 to `ymm` or `zmm`.
`div_const` on `u64` times at 1.06 of scalar although its auto loop is partially vectorized, because the baseline build already uses SSE2 shifts and scalar `mul`, so both builds have the same shape.

## Intrinsics decisions

The priority followed the acceptance queries: `histogram`, `reduce_into`, `div_const`, then `gather` and `scan`.
Intrinsics are committed where a hand-written entry beat the `auto` entry in the interpreter bench, and the other kernels are strain cases with the measurement that decided them.
`tests/isa_variants.rs` checks 39 AVX2 and 43 AVX-512 intrinsics kernels against the scalar entries.

### Committed

* `gather` on 64-bit rows (`i64`, `u64`, `f64`): the entries `gather::avx2` and `gather::avx512` in `src/kernels/x86/gather.rs` reuse the scalar body's argument and bounds check, then load rows with `vpgatherqq`. They run at 0.80 and 0.83 of scalar and within 1.04x of the native gather loop. The cost is on small sources: for a 65536-row (512 KB) source the hardware gather measured 9.85 ms (`ymm`) and 11.03 ms (`zmm`) against 9.34 ms for the scalar `avx512` build, 1.05x and 1.18x slower, in a standalone prototype. The entry is installed for every source size, so the intrinsics backend pays this on mid-sized sources. TPC-H q01's `gather(counts, groups)` has such a source but gathers only its few non-empty groups, so the cost there is negligible. 32-bit, `u8`, and bool gathers keep the `auto` entry.
* `scan_by` add on `i64` and `u64`, AVX-512 only: the entry `scan::update_avx512` runs a segmented log-step with the start flags in a mask register, and it reaches 0.81 of scalar in the interpreter. In a standalone prototype at 10M rows it ran 4.99 ms against 7.01 ms scalar at start probability 1/16, with the same result at 1/2 and 1/1024. The AVX2 version of the same step ran 7.10 ms, the scalar loop's speed.

### Strain cases

* `histogram` and `reduce_into`: scalar bucket loop on AVX2 and AVX-512, with a vectorized bounds pass. A standalone prototype with the kernels' clamp and bounds semantics tried both techniques the spec names. An AVX-512 `vpconflictq` histogram ran 10.13 ms against 5.56 ms for the scalar loop on 10M uniform keys, and 8 replicated sub-histograms with gather and scatter ran 9.62 to 9.73 ms, so both lose by 1.5x to 1.9x on the bench's uniform keys. Scatter is slow on this core, and the scalar loop is not latency-bound even with 4 keys, because Zen 5 handles repeated increments of one address well. On two skewed shapes `vpconflictq` was the fastest variant (0.87 and 0.54 ms against 1.16 and 0.89 ms scalar), but the prototype did not isolate why, and it needs AVX512CD, which `Isa::Avx512` does not check.
* `div_const` on 64-bit types: the multiply-high is a scalar `mul` per lane, because neither AVX2 nor AVX-512 has a 64-bit multiply-high. The rest of the computation is vector code, so the `i64` auto entry runs at 0.65 of scalar and 0.85 of the native `x / 60` loop. A `vpmuludq` emulation of the multiply-high was not attempted.
* `scan` on integers: scalar loop on both ISAs. The in-register log-step prototype ran 4.04 ms against 4.17 ms scalar into a preallocated buffer, a gain of 3% that sits inside the run-to-run noise of the interpreter bench (scalar 7.14 to 7.40 ms across runs), and the scan is memory-bound at 10M rows.
* `scan_by` add on AVX2: scalar loop, because the segmented log-step needs `vpermq` plus a blend for a one-lane shift and `vperm2i128` for a two-lane shift, and it ran at the scalar loop's speed. Other `scan_by` folds (`min`, `max`, `mul`, the bitwise folds) and `scan_by` on 32-bit and 8-bit inputs are scalar loops on both ISAs, because they were not prototyped. The integer `min`, `max`, and bitwise folds have the same select-plus-op chain and could take the same segmented form.
* `argsort`: scalar sort. The sort is the baseline build of `sort_unstable_by_key` on every ISA, and only the index initialization is compiled for the ISA, at 0.10 GB/s.
* `gather` on NEON has no instruction, so the aarch64 section records it as a strain case whatever it measures.

`prev` is a `memcpy`, already vectorized by libc, and `and`, `or`, `xor`, and `not` are vectorized and run at the bandwidth of `add`.

The gap to native is largest for `histogram` (1.72x) and `reduce_into` (1.94x).
The native loop is one pass that relies on Rust's bounds-checked indexing, while the kernel reads the keys twice, once for the order-independent error check and once for the buckets.
A fused single-pass variant (clamp, OR the out-of-range flag, report the first bad key only on the error path) gained 13% for `histogram` and 25% for `reduce_into` in the prototype.
It keeps the error independent of row order and applies to the scalar and `auto` entries alike, so it is a plan 5 candidate.

Six of seven queries are faster than both corgi and DuckDB on one thread.
The TPC-H q01 ratio against corgi uses its `q01` time (48.92 ms), and against its `q01b` variant (39.72 ms) the best Verkehrt time gives 0.48.
ClickBench q42 is the exception, at 3.05x DuckDB and 2.61x corgi, and it is the only query slower than either.
The first acceptance run (commit 9bb5e11, before the inline fix and the gather entries) agrees within 5% on most queries and variants, and `run1.tsv` in the results has it.
Exceptions that are slower in the final run: ClickBench q07 `avx2-auto` by 20.6% (0.681 ms then, 0.822 ms in both final runs), TPC-H q01 `avx2-intrinsics` by 9.1% and `scalar` by 6.3%, and TPC-H q06 by 5.5% to 6.2% for `avx2-auto`, `avx512-auto`, and `avx512-intrinsics`.
The q07 change appeared after the inline fix and its cause was not investigated.

How each query is planned (from `--plan` output, `task-11-plans.txt`):

* ClickBench q01 and q02 plan to one fused kernel each (`count_ne_i64`, and `reduce_add_i64` plus `length_i64`), q06 to `reduce_min_i64` and `reduce_max_i64`, and TPC-H q06 to one `dot_i64` over two `compress_i64` outputs behind a chain of comparison and `and_bool` kernels.
* ClickBench q07 plans a `filter_ne_i64`, a `histogram`, a `where`, two `gather_i64`, and one `argsort_i64` over the handful of result groups, which is why `argsort` is in plan 4.
* ClickBench q42 plans a nine-kernel mask chain (five comparisons and four `and_bool`), `compress_i64`, `div_const_i64`, `histogram`, `where`, and `slice_i64`.
* TPC-H q01 plans a combined 16-bit key built from `cast_u8_i64` of the two flag columns, a `histogram` over 65536 buckets, one `reduce_into_add_i64` per sum, and `gather_i64` at the non-empty groups.

### Known limit: no NULL

On an empty input, SQL aggregates return NULL, and Verkehrt has no NULL.
On an empty table, TPC-H q06 and ClickBench q02 return 0 (and NaN for q02's average), and ClickBench q06 fails with the empty-array error of `reduce` with `min` or `max`.
The queries match DuckDB on the real data, where no table is empty.
The programs do not guard the empty case, because a guard would need a NULL design, and that decision belongs to the user.

### The first gap to close: ClickBench q42

ClickBench q42 is slower than both corgi and DuckDB, so it is the first gap for plan 5.
This document does not profile the query per kernel.
The program's data does give a candidate cause: the filter keeps 376,905 of the 1,000,000 rows, whose minute keys (`EventTime / 60`) have 1,440 distinct values but a maximum of 22,898,639.
The program takes its bucket count from `max(minute) + 1`, so `histogram` allocates and zeroes 22,898,640 buckets (183 MB of `i64`), and `where(counts > 0)` scans all of them to find 1,440 groups.
A grouping that sizes its buckets by the key range (`max - min + 1`) or by sort or hash on the keys is the direction that removes this, and plan 5 plans grouping on many distinct keys anyway.
This is derived from the program and the data, and a per-kernel trace of q42 should confirm it before any design work starts.

No query shows a fused-kernel candidate by measurement, because the traces were not collected.
The plans show two shapes that run as separate passes: the nine-kernel mask chains of q42 and TPC-H q06 each materialize a `bool[]` per step.
A fused predicate kernel is a candidate only if a per-kernel trace shows these passes taking a large share of the query time.

## Plan 5 candidates

* Fuse the bounds check into the bucket loop of `histogram` and `reduce_into`: 13% to 25% in the prototype.
* Add a constant relation to the egglog prelude, so `reduce_into` with a fill of 1 can plan to `histogram`.
* Close ClickBench q42, the only acceptance query slower than both references, starting with a per-kernel trace.
* Add a regression check that the `auto` entries of whole kernels contain the ISA's vector code.
