# Tier 1 kernels on x86: measurements

This document compares Verkehrt's tier 1 kernels against native Rust loops at 10M elements and sweeps the vector length to find where dispatch overhead stops dominating.
The spec's target is throughput within 1.5x of a native Rust baseline on AVX2 and AVX-512 for `sum`, `sum(x * y)`, `count(x > c)`, and `filter(x, |v| v > c)`.
Each table below gives the interpreter variants and the native baselines for one workload, and the last section gives the crossover sweep.
All numbers come from one run of the command below, so run-to-run variation is not quantified.

Command:

```
CARGO_INCREMENTAL=0 cargo bench --locked --bench tier1
```

No other build or benchmark ran during measurement.
The bench is `benches/tier1.rs`.
Criterion ran with `sample_size(10)`, a 0.5 s warm-up, and a 3 s measurement time for the 10M workloads, and with `sample_size(20)`, 0.1 s warm-up, and 0.3 s measurement time for the crossover sweep.
All times, GB/s, and ratios are computed from criterion's median estimates, and GB/s is decimal (10^9 bytes per second).

## What the variants are

* `scalar`: the interpreter with `--isa scalar`. The scalar entries are portable Rust compiled for the baseline x86-64 target, and the compiler vectorizes the shared loops with SSE2: the release bench binary's `<Dot<f64> as Reducer>::update` (scalar entry, found with `objdump -d --no-show-raw-insn`) contains 8 `mulpd` and 8 `addpd` on `xmm` registers and no `ymm` or `zmm` use. So "scalar" means portable code on the baseline target, not one element per instruction.
* `avx2-auto` and `avx512-auto`: the interpreter with `--isa avx2|avx512 --backend auto`, the same portable loops compiled under `#[target_feature]`. The `intrinsics` backend currently resolves to the auto entries, so it is not measured separately.
* `native-base`, `native-avx2`, `native-avx512`: plain Rust loops in the bench file, compiled for the baseline target and under the same feature strings as the kernels. `native-base` is the comparison for `scalar`, and `native-avx2` and `native-avx512` are the comparison for the matching `-auto` variants.
* Native `sum` and `dot` use the canonical 16-accumulator order over `as_chunks::<16>()`, with no FMA. The bench asserts that every interpreter variant and every native baseline return the same bits for `sum` and `dot`, the same count for `count`, and the same rows for `filter`, before timing.
* Native `filter` is a predicated store (write `x[i]` at the output index, advance the index by the comparison result) into a zeroed `Vec` of capacity `n`. The interpreter's `filter` entry builds its output with `x.iter().copied().filter(..).collect()`, a data-dependent branch per element (`src/kernels/scalar/fused.rs`).
* The interpreter timing is `Prepared::execute` only, prepared once outside the timed loop. It includes cloning the input `Value`s, output allocation, and the dispatch of the plan.
* The bench also asserts, at length 10_000_007 (not a multiple of 16), that every interpreter variant and native baseline return the same bits for `sum` and `dot`, so the canonical tail is exercised.
* Inputs are `rand_f64(10_000_000, 1)` and `rand_f64(10_000_000, 2)` (80 MB each), generated by the interpreter. The comparison constants are 0.5 for `count`, and 0.99, 0.5, and 0.01 for `filter`. The bench asserts the match fraction is within 0.5 percentage points of `1 - c`, and the observed match counts are 99,695 (0.997%), 4,998,931 (49.989%), and 9,899,130 (98.991%) of 10,000,000 rows.
* GB/s counts input bytes read: 80 MB for `sum`, `count`, and `filter`, and 160 MB for `dot`. The output of `filter` is not counted.

## Memory bandwidth reference

A plain `copy_from_slice` of 10M `f64` (reads 80 MB, writes 80 MB) takes 3.311 ms, which is 48.3 GB/s of combined read and write traffic.
A read-only bandwidth was not measured separately.

## Reading the results

`sum`, `dot`, and `count` are within 1.04x of the native baseline of the same ISA on both AVX2 and AVX-512.
The interpreter's `-auto` variants and the matching native baselines run at 39 to 49 GB/s of input, which is close to the 48.3 GB/s combined read and write traffic of the copy loop.
That is consistent with these three workloads being limited by memory at 10M elements, but a read-only bandwidth was not measured, so the memory limit is not established.
At 10M elements the scalar variant is 2 to 25% slower than the AVX2 and AVX-512 variants for these workloads (`dot` 4.169 ms against 4.027 to 4.095 ms, `count` 2.227 ms against 1.784 to 1.823 ms), and it tracks `native-base` within 4%.

The `filter` rows at 1% selectivity pass at 1.05x and 1.06x.
At 50% and 99% selectivity they miss the target at about 11x and 3.2x.
The scalar, AVX2, and AVX-512 variants take nearly the same time in each case, with spreads (largest over smallest) of 1.5% at 1% selectivity (5.417 to 5.499 ms), 0.2% at 50% (67.859 to 68.016 ms), and 0.5% at 99% (24.282 to 24.406 ms), so no ISA effect shows.
The times are consistent with the interpreter's branchy `filter` entry, which does not use the ISA, but the cause of the slowdown was not measured.
The native baseline uses a predicated store instead of a branch, so the comparison is between two different algorithms and not only between two builds of one.
Whether a branch-free scalar `filter` entry closes the gap was not tested.

## Crossover

The crossover sweep uses the best available ISA with the `auto` backend (`avx512-auto`) and the matching native baseline (`native-avx512`).
`sum` is `sum(x)`, and `mul` is `x * y` returning a new array, so its interpreter and native timings include output allocation.
The crossover length is the smallest `n` from which the interpreter stays within 1.5x of native for all larger `n` in the sweep.
Inputs are prefixes of the same 2^20-element arrays (8 MB each at the largest size), so the small sizes run from cache. The sweep was run a second time after the native call's availability check was moved out of the timed closure, and this table is the second run.

| 2^8 | 281 | 10 | 29.51 | 437 | 81 | 5.39 |
| 2^9 | 292 | 17 | 17.36 | 502 | 134 | 3.75 |
| 2^10 | 302 | 36 | 8.31 | 544 | 280 | 1.95 |
| 2^11 | 350 | 80 | 4.40 | 728 | 487 | 1.49 |

The first length at which the interpreter is within 1.5x is 2^14 = 16384 for `sum` (1.33) and 2^11 = 2048 for `mul` (1.49).
Neither holds for all larger sizes, since `sum` is 1.58 at 2^16 and `mul` is 1.52 at 2^12. By the stricter definition above the crossover length is 2^17 = 131072 for `sum` (1.09 from there on) and 2^13 = 8192 for `mul` (1.41 from there on).
An earlier run of this sweep, whose timed closure still contained a per-iteration availability assert in the native call, gave 2^14 for `sum` and 2^12 for `mul` under the strict definition. The two runs differ by more than the ratios near 1.5 can resolve (for example native `sum` at 2^16 took 3359 ns then and 2914 ns now), so the crossover lengths are good to about one power of two.
For `sum` the interpreter time is flat at about 270 ns from 16 to 128 elements, so a fixed per-call cost of roughly 270 ns dominates there.
The `mul` interpreter time is flat at about 360 ns over the same range.
Between 2^9 and 2^16 elements the native `sum` of a cached array reaches 139.5 to 243.3 GB/s and the interpreter reaches 14.0 to 116.0 GB/s, so the in-cache ratio is the harshest comparison in this document.
The `mul` ratios at 2^16 to 2^20 (1.08 to 1.29) are not monotonic, and with one run of 20 samples per row the differences between those rows are not shown to be larger than noise.
