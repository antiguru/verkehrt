# Tier 1 kernels on x86: measurements

This document compares Verkehrt's tier 1 kernels against native Rust loops at 10M elements and sweeps the vector length to find where dispatch overhead stops dominating.
The spec's target is throughput within 1.5x of a native Rust baseline on AVX2 and AVX-512 for `sum`, `sum(x * y)`, `count(x > c)`, and `filter(x, |v| v > c)`.
Each table below gives the interpreter variants, the native baselines, and corgi for one workload, and the last section gives the crossover sweep.
The `sum`, `dot`, `count`, corgi reduction, and crossover numbers come from one run of the commands below, so their run-to-run variation is not quantified.
The `filter` numbers come from later runs after two changes to the selection kernels, described in the section on selection.

The benches are `benches/tier1.rs` and `benches/corgi.rs`, and the two ran separately.

All times, GB/s, and ratios are computed from criterion's median estimates, and GB/s is decimal (10^9 bytes per second).

## What the variants are

* `scalar`: the interpreter with `--isa scalar`. The scalar entries are portable Rust compiled for the baseline x86-64 target, and the compiler vectorizes the shared loops with SSE2: the release bench binary's `<Dot<f64> as Reducer>::update` (scalar entry, found with `objdump -d --no-show-raw-insn`) contains 8 `mulpd` and 8 `addpd` on `xmm` registers and no `ymm` or `zmm` use. So "scalar" means portable code on the baseline target, not one element per instruction.
* `avx2-auto` and `avx512-auto`: the interpreter with `--isa avx2|avx512 --backend auto`, the same portable loops compiled under `#[target_feature]`. For `sum`, `dot`, and `count` the `intrinsics` backend resolves to the auto entries, so it is not measured separately.
* `avx2-intrinsics` and `avx512-intrinsics`: the interpreter with `--backend intrinsics`, measured for `filter` only, the one workload with intrinsics entries.
* `native-base`, `native-avx2`, `native-avx512`: plain Rust loops in the bench file, compiled for the baseline target and under the same feature strings as the kernels. `native-base` is the comparison for `scalar`, and `native-avx2` and `native-avx512` are the comparison for the matching `-auto` variants.
* Native `sum` and `dot` use the canonical 16-accumulator order over `as_chunks::<16>()`, with no FMA. The bench asserts that every interpreter variant and every native baseline return the same bits for `sum` and `dot`, the same count for `count`, and the same rows for `filter`, before timing.
* Native `filter` is a predicated store (write `x[i]` at the output index, advance the index by the comparison result) into a zeroed `Vec` of capacity `n`. In the first run the interpreter's `filter` entry built its output with `x.iter().copied().filter(..).collect()`, a data-dependent branch per element (`src/kernels/scalar/fused.rs`). The section on selection describes the predicated entry that replaced it.
* The interpreter timing is `Prepared::execute` only, prepared once outside the timed loop. It includes cloning the input `Value`s, output allocation, and the dispatch of the plan.
* The bench also asserts, at length 10_000_007 (not a multiple of 16), that every interpreter variant and native baseline return the same bits for `sum` and `dot`, so the canonical tail is exercised.
* Inputs are `rand_f64(10_000_000, 1)` and `rand_f64(10_000_000, 2)` (80 MB each), generated by the interpreter. The comparison constants are 0.5 for `count`, and 0.99, 0.5, and 0.01 for `filter`. The bench asserts the match fraction is within 0.5 percentage points of `1 - c`, and the observed match counts are 99,695 (0.997%), 4,998,931 (49.989%), and 9,899,130 (98.991%) of 10,000,000 rows.
* `corgi`: the same workload in corgi, Frank McSherry's columnar interpreter, at the revision `2751e04e8501d47b33219be23049bf4afa7a4428` that DDIR pins (`benches/corgi.rs`). Corgi has no flat column type, so a column is one row holding the whole column as a list, the form its own `benches/idioms.rs` uses (`Value::List(Bounds::offsets(vec![N]), ..)`). Floats are stored as total-order `u64` keys and the reductions run in row order. The timing is `Program::run` only, with the program compiled once through `Program::compile_ml` (which runs corgi's optimizer), and it includes the `Arc` clone of the input, output allocation, and dropping the output. Inputs are the same `rand_f64` arrays as for `tier1`, converted into corgi values before timing, and the throughput bytes are the same. Criterion settings are the same (`sample_size(10)`, 0.5 s warm-up, 3 s measurement). The programs are:
  * `sum`: `input fold_add`
  * `dot`: `input map (r -> (r.0, r.1) mul) fold_add`, over a list of pairs
  * `count`: `input map (v -> (v, 0.5) gt) fold_add`
  * `filter`: `input map (e -> ((e, C) gt, e)) filter`, with `C` of 0.99, 0.5, and 0.01
* The `corgi` rows have no same-ISA native baseline, so their ratio columns are `-`. The section on corgi below compares them with `avx512-auto` and `native-avx512`.
* GB/s counts input bytes read: 80 MB for `sum`, `count`, and `filter`, and 160 MB for `dot`. The output of `filter` is not counted.

## Memory bandwidth reference

A plain `copy_from_slice` of 10M `f64` (reads 80 MB, writes 80 MB) takes 3.311 ms, which is 48.3 GB/s of combined read and write traffic.
A read-only bandwidth was not measured separately.

## Selection: branch-free bodies and the intrinsics backend

The first run measured `filter` at 11x of native at 50% selectivity and 3.2x at 99%, with no ISA effect.
Two changes followed, and each was measured separately.
Step 0 rewrote the portable selection bodies (`compress_*`, `where`, `filter_*_*`) in predicated form: every row is written to the output position, and the position advances by the keep flag.
They write into reserved builder capacity (`ArrayBuilder::spare_rows` and `commit`), 2048 rows per chunk, instead of collecting each tile into a temporary `Vec`, and reserve the whole tile's rows up front.
Step 0 changes the scalar and auto entries, so it also changes the baseline that the intrinsics entries are compared with.

The intrinsics backend then added hand-written entries for the same kernels.
On AVX-512 the keep mask comes from a compare into a mask register (`filter`) or a byte test of the bool mask (`compress`, `where`), and `vpcompressq`/`vpcompressd` packs the kept lanes, with the VBMI2 byte compress for `u8` and bool.
On AVX2 the lane mask from `movemask` indexes a table of `vpermd` permutations for 32- and 64-bit rows.
AVX2 has no `u8` or bool entry, so `compress_u8` and `compress_bool` use the auto entry on AVX2.

Two intermediate versions of step 0 were also timed and profiled with `perf`.
Without the up-front reservation, the builder grew by reallocation, and 50% took 10.8 ms.

The step 0 commit therefore shrank only when more than 7 of 8 reserved blocks were unused.

Its effect is measured in "The capacity bound" below.

#### Build drift

The auto and `native-base` medians of this build differ from the step 0 run, although their code did not change between the two commits.
At 1%, `avx2-auto` took 7.145 ms here and 5.248 ms at step 0, and `native-base` took 7.029 ms here and 5.268 ms at step 0.
Both stayed at 7.1 ms when run alone, unpinned, from this binary, and the three pinned runs agree within 0.7% for both.
The first run of this document also measured `native-base` at 5.315 ms, and an unpinned run of an intermediate build gave 6.971 ms.
So these medians move by up to 1.36 times (5.248 to 7.145 ms) between builds of unchanged code, and the cause was not measured.
The auto ratios in this table are therefore not a better estimate than the step 0 ratios (1.02 to 1.19).
For the same reason the auto-against-intrinsics speedup is given across both builds.
Against the intrinsics medians above, the step 0 auto medians give 1.14 to 1.27 on AVX2 and 1.31 to 1.74 on AVX-512, and this build's auto medians give 1.36 to 1.73 on AVX2 and 1.39 to 1.85 on AVX-512.
The intrinsics entries are faster than auto in every case, by 1.14 to 1.85 times.

## Corgi

## Reading the results

`sum`, `dot`, and `count` are within 1.04x of the native baseline of the same ISA on both AVX2 and AVX-512.
The interpreter's `-auto` variants and the matching native baselines run at 39 to 49 GB/s of input, which is close to the 48.3 GB/s combined read and write traffic of the copy loop.
That is consistent with these three workloads being limited by memory at 10M elements, but a read-only bandwidth was not measured, so the memory limit is not established.
At 10M elements the scalar variant is 2 to 25% slower than the AVX2 and AVX-512 variants for these workloads (`dot` 4.169 ms against 4.027 to 4.095 ms, `count` 2.227 ms against 1.784 to 1.823 ms), and it tracks `native-base` within 4%.

In the first run the `filter` rows at 1% selectivity passed at 1.05x and 1.06x, and at 50% and 99% selectivity they missed the target at about 11x and 3.2x.
The scalar, AVX2, and AVX-512 variants took nearly the same time in each case, with spreads (largest over smallest) of 1.5% at 1% selectivity (5.417 to 5.499 ms), 0.2% at 50% (67.859 to 68.016 ms), and 0.5% at 99% (24.282 to 24.406 ms), so no ISA effect showed.
The first run's native medians were 5.315, 5.200, and 5.211 ms at 1% (base, AVX2, AVX-512), 6.205, 6.120, and 6.134 ms at 50%, and 7.670, 7.656, and 7.636 ms at 99%.
A branch-free predicated entry, the same algorithm as the native baseline, brought the auto variants to 1.02 to 1.19x of native, and the intrinsics entries to 0.59 to 1.09x, see the section on selection.
Bounding the retained capacity to twice the output then made the 50% case 2.8 to 3.5 ms slower, to 1.29 and 1.45x for the intrinsics entries.

## Crossover

The crossover sweep uses the best available ISA with the `auto` backend (`avx512-auto`) and the matching native baseline (`native-avx512`).
`sum` is `sum(x)`, and `mul` is `x * y` returning a new array, so its interpreter and native timings include output allocation.
The crossover length is the smallest `n` from which the interpreter stays within 1.5x of native for all larger `n` in the sweep.
Inputs are prefixes of the same 2^20-element arrays (8 MB each at the largest size), so the small sizes run from cache. The sweep was run a second time after the native call's availability check was moved out of the timed closure, and this table is the second run.

| n | sum interp (ns) | sum native (ns) | sum ratio | mul interp (ns) | mul native (ns) | mul ratio |
|---|---|---|---|---|---|---|

The first length at which the interpreter is within 1.5x is 2^14 = 16384 for `sum` (1.33) and 2^11 = 2048 for `mul` (1.49).
Neither holds for all larger sizes, since `sum` is 1.58 at 2^16 and `mul` is 1.52 at 2^12. By the stricter definition above the crossover length is 2^17 = 131072 for `sum` (1.09 from there on) and 2^13 = 8192 for `mul` (1.41 from there on).
An earlier run of this sweep, whose timed closure still contained a per-iteration availability assert in the native call, gave 2^14 for `sum` and 2^12 for `mul` under the strict definition. The two runs differ by more than the ratios near 1.5 can resolve (for example native `sum` at 2^16 took 3359 ns then and 2914 ns now), so the crossover lengths are good to about one power of two.
For `sum` the interpreter time is flat at about 270 ns from 16 to 128 elements, so a fixed per-call cost of roughly 270 ns dominates there.
The `mul` interpreter time is flat at about 360 ns over the same range.
Between 2^9 and 2^16 elements the native `sum` of a cached array reaches 139.5 to 243.3 GB/s and the interpreter reaches 14.0 to 116.0 GB/s, so the in-cache ratio is the harshest comparison in this document.
The `mul` ratios at 2^16 to 2^20 (1.08 to 1.29) are not monotonic, and with one run of 20 samples per row the differences between those rows are not shown to be larger than noise.
