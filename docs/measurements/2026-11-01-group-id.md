# Grouping without sorting: measurements

This document compares `group_id` with the sort-based grouping idiom, and records the two tuning choices that the measurement supported: a faster table growth for mostly distinct columns, and a random hash multiplier per call.
`group_id` assigns each row the dense id of its key by first occurrence, with a hash table.
The sort idiom is the one of `tests/acceptance/clickbench/q30.vk`: stable `argsort` passes by each key, a run-start mask, and a scan that numbers the runs.
The hash table wins by 2.3x to 11x on inputs with repeated keys, and ties or loses on columns that are almost all distinct.
The kernel needs no vector variant, since the `auto` entries of both x86-64 levels run within noise of scalar.

## Setup

| Item | Value |
|---|---|
| CPU | AMD Ryzen AI MAX+ 395 (Zen 5, 32 logical CPUs) |
| Frequency scaling | boost off, governor `powersave`, 3.0 GHz under load (user-reported, not recorded during the runs) |
| Kernel, rustc | 7.2.11+deb14-amd64, 1.99.0 |
| Profile | release (LTO, `codegen-units = 4`), `CARGO_INCREMENTAL=0` |
| Harness | `tier2_group` in `benches/tier1.rs`, criterion with `sample_size(10)`, a 0.5 s warm-up, and a 3 s measurement time, timing `Prepared::execute` |

Every bench checks its answer before timing it: `group_id` against a `HashMap` oracle, and the sort idiom against a stable sort of the rows.
The tables give the criterion mean in ms.
Every raw file starts with the load average before the run and ends with the one after it, and the 1-minute values ranged from 1.3 to 5.2.
Differences within about 10% are noise on this host.

### Inputs

Each shape has 1M and 10M rows of one `i64` column, and a second `i64` column for the two-column form.

* `uniform`: both columns uniform over the full `i64` range, so nearly every row has a new key.
* `d80k`: the first column draws from a pool of 80,000 values, the ClickBench `UserID` shape at 1M rows. The second column is the pool index modulo 7, so the pair has 80,000 distinct values too.
* `d1m`: a pool of 1,000,000 values, which is 63% distinct at 1M rows and 10 rows per value at 10M.
* `d10`: a pool of 10 values.

The sort idiom returns ids in sorted order and gathers no payload, while `group_id` returns ids in row order, so the idiom is the cheaper of the two outputs and the comparison favors it.

The hash table wins by 3.3x to 11x on the `d80k` and `d10` shapes, where the table stays small and in cache.
It loses on single columns that are mostly distinct at 1M rows, by 1.4x to 1.6x, and ties the idiom on the 10M uniform column.
Those inputs make the table large and every insert a cache miss, while the radix sort streams memory.
The two-column form fares better than the single column because the idiom sorts and gathers twice, and `group_id` hashes the pair in one pass.
The cost model of the sort idiom also leaves out the payload gathers that a query adds per column, which `group_id` avoids, so the table above understates the query-level gain, which the later query measurement covers.

The `x86-64-v3` and `x86-64-v4` `auto` entries compile the same loop, and every one of their times is within 6% of scalar (at most 5.4% on the two-column 10-key shape at 1M rows) (`final-hash-1M.txt`, `final-hash-10M.txt`).
No ISA-specific variant is justified.

## Growth of the table

The first kernel doubled the table after every insert that left it more than half full, from 256 slots.
On the 10M uniform column that took 538.6 ms, against 237.9 ms when the table was sized for 2^25 slots up front (`probe-presize-10M.txt`), so rehashing at every size cost more than the inserts themselves.
A kernel cannot know the distinct count in advance, so growth now looks at how many rows opened a group.
When at least 7/8 of the rows so far opened a group, the table grows 16x instead of 2x, and from 1M slots on it goes straight to the table for twice the row count, the largest one that can be needed.
Growth never exceeds that table, so the worst case allocates what an all-distinct column needs anyway.

Scalar times in ms for the 10M uniform column and the other shapes:

| Step | `uniform` 10M | `uniform` pair 10M | `d80k` 10M | `d1m` 1M | `d1m` 10M |
|---|---|---|---|---|---|
| Doubling (first kernel) | 538.6 | 655.2 | 64.3 | 35.6 | 161.4 |
| 16x jump only | 417.2 | 517.8 | 67.3 | | |
| 16x jump, then straight to the largest | 269.0 | 333.3 | | 30.4 | 170.0 |
| Final (with the random multiplier) | 243.5 | 335.5 | 61.4 | 28.4 | 157.4 |
| Table sized up front (probe) | 237.9 | | 58.3 | | |

Sources are `baseline-hash-10M.txt`, `doubling-d1m.txt`, `jump-10M.txt`, `jump2-10M.txt`, `jump2-d1m.txt`, `final-hash-*.txt`, and `probe-presize-10M.txt`.
The change halves the time on the 10M uniform column, comes within 3% of the up-front size on one column, and gains 20% on `d1m` at 1M rows.
It leaves `d80k` and the 10-key shape unchanged within noise: a column that repeats keys stops meeting the 7/8 test after the first growths, and a 10-key column never grows.
The 1M-pool column at 10M rows (`d1m`) is the case where the heuristic could overshoot, and its 5% difference is within noise (161.4 against 170.0 ms with the straight jump, 157.4 ms in the final kernel).

The growth step also moved into a cold, non-inlined function.
With the growth inline, the 10-key case ran 25% slower than the first kernel (2.13 against 1.71 ms at 1M rows, `seed-off.txt` and `probe-head-d10.txt`), and moving the growth out fixed it, so the cause is the code layout of the hot loop, which was not examined further.
After the move it is within 5% (`final-cold-d10.txt`: 1.77 ms).

## Hash multiplier

`mix` multiplies the xorshift-folded key by an odd constant, so it is a bijection, public and deterministic.
A set of keys that all land in one slot, or pairs with equal full hashes, then makes linear probing quadratic, and the tests build both.
The ids do not depend on the hash, so `group_id` now draws one random odd multiplier per call from `RandomState`, which std seeds from the operating system, and the output stays identical for every multiplier.
Multiply-shift hashing with a random odd multiplier is a standard universal family, and chosen keys no longer collide without knowing it.
The two-column hash `mix(mix(a) ^ b)` uses the same multiplier twice.

Scalar times in ms, with the fixed multiplier `0x9E37_79B9_7F4A_7C15` and with the random one, on the final code (`seed-off-final.txt` against `final-hash-1M.txt` and `final-hash-10M.txt`):

| Shape | Columns | 1M fixed | 1M random | 10M fixed | 10M random |
|---|---|---|---|---|---|
| `uniform` | 1 | 28.95 | 28.66 | 254.1 | 243.5 |
| `uniform` | 2 | 37.61 | 38.24 | 336.5 | 335.5 |
| `d80k` | 1 | 8.71 | 8.42 | 64.5 | 61.4 |
| `d80k` | 2 | 10.44 | 10.38 | 77.6 | 78.6 |
| `d1m` | 1 | 29.52 | 28.39 | 158.6 | 157.4 |
| `d1m` | 2 | 38.37 | 37.92 | 246.5 | 242.9 |
| `d10` | 1 | 1.79 | 1.78 | 20.1 | 19.6 |
| `d10` | 2 | 2.30 | 2.60 | 25.1 | 27.5 |

Of the 16 pairs, 14 differ by 5% or less, with both signs.
The two-column `d10` pairs are 7% to 13% slower with the random multiplier, in all three paired runs (`seed-off.txt` against `seed-on.txt`, the `d10` reruns, and the final pair).
That shape is the hot-cache one, where each row is a short dependent chain of two multiplies, and the multiplier is now a register instead of an immediate.
The cost is at the edge of the noise band and shows nowhere else, so the kernel adopts the random multiplier: it removes a quadratic worst case that any caller with chosen keys could trigger, and the ids are unchanged.

The oracle tests prove the independence from the multiplier, since every call in them draws a new one.
Two tests fix the multiplier instead, to keep the worst cases alive: `colliding_keys_under_the_real_hash` runs keys that all pick slot 0 under it, and `pairs_with_equal_full_hashes` runs pairs with equal full hashes.

## Choices not changed

* Linear probing, the 1/2 load bound, and the hash shape stay. Nothing in these measurements points at them, and the 10M uniform time is within 3% of a table sized up front.
* The single `u8` column keeps its direct 256-entry table, and `u8` pairs hash. The `u8` single column was not benched against a hashed variant, because the direct table has no probing to tune and cannot be slower than a hash lookup.
* A table of ids that reads keys back from the input, 4 bytes per slot instead of 16, could help the mostly distinct shapes, where the table is large. It was not prototyped, and it is the next step if those shapes matter.

## Strain cases

* Adversarial keys are covered by the random multiplier. A caller that knows the multiplier is outside the model.
* Mostly distinct columns of up to a few million rows are 0.6x to 0.9x of the sort idiom on one column. The table does not fit in cache there, so each insert misses, and no vector variant changes that.
* `group_id` has no vector variant on any ISA, and the measurement above is the reason: the `auto` entries on both x86-64 levels are within noise of scalar, and the loop is bound by cache misses and the dependent probe.
