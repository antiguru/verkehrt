# Kernels and acceptance queries on M5 Max: Measurements

This record measures commit `0acd7d5` on an Apple M5 Max. It covers tier 1 and tier 2 kernels at 10 million rows, the dispatch crossover sweep, grouping at 1 and 10 million rows, all 20 ClickBench acceptance programs, and both TPC-H acceptance programs. Corgi and DuckDB were measured on the same machine with the corresponding data. The earlier [x86 measurements](2026-10-31-tier2.md) use a different host and earlier code, so their absolute times are not directly comparable.

## Setup and method

| Item | Value |
|---|---|
| CPU, OS | Apple M5 Max, arm64, Darwin 27.2.0 |
| Power | AC, battery charged |
| Revision, compiler | `0acd7d52c033ef2b7731850dfa882bc77a71eef3`, rustc 1.99.1 |
| Build | Release profile with LTO, `CARGO_INCREMENTAL=0`, `--locked` for Verkehrt |
| Corgi | `2751e04e8501d47b33219be23049bf4afa7a4428` |
| DuckDB | 1.5.6, `SET threads = 1` for the reference column |
| ClickBench | `hits_0.parquet`, 1,000,000 rows, prepared by `scripts/prepare-acceptance.sh` |
| TPC-H | Scale factor 0.2, prepared by the same script |

Verkehrt's numbers are Criterion means with 10 samples, a 0.5-second warm-up, and a 3-second measurement period per variant, except for the crossover sweep, which uses 20 samples, a 0.1-second warm-up, and a 0.3-second measurement period. The kernel and query timers cover `Prepared::execute`, excluding parsing, planning, and input loading; the kernel benchmark checks output against its reference before timing. The `scalar` label means the baseline aarch64 build, which the compiler may vectorize with NEON; `neon-intrinsics` uses hand-written entries where installed and otherwise falls back to those same scalar entries. Corgi's query benchmarks report the best of at least three executions, while DuckDB reports its best repeated one-thread run, so those columns use a more favorable statistic than the Criterion mean.

Raw results are in [bench-tier1.txt](2026-11-02-m5/bench-tier1.txt), [bench-crossover.txt](2026-11-02-m5/bench-crossover.txt), [bench-corgi-tier1.txt](2026-11-02-m5/bench-corgi-tier1.txt), [bench-tier2.txt](2026-11-02-m5/bench-tier2.txt), [bench-clickbench.txt](2026-11-02-m5/bench-clickbench.txt), [bench-tpch.txt](2026-11-02-m5/bench-tpch.txt), [corgi-clickbench.txt](2026-11-02-m5/corgi-clickbench.txt), and [corgi-tpch.txt](2026-11-02-m5/corgi-tpch.txt). Verkehrt was run with `cargo bench --locked --bench tier1 -- 'tier1/' --noplot`, then `'crossover/'` and `'tier2/'`, and `cargo bench --locked --bench acceptance -- 'acceptance/SUITE/' --noplot`, with the corresponding `VERKEHRT_CLICKBENCH` or `VERKEHRT_TPCH` directory set. Corgi's `clickbench` and `tpch` benchmarks used the same prepared directories via `CORGI_CLICKBENCH` and `CORGI_TPCH`, with the names of Verkehrt's queries as filters. Release-mode tests with both prepared directories set ran 331 tests, all passing, with one skipped by nextest; these include the checks against DuckDB's saved answers for both suites ([test log](2026-11-02-m5/acceptance-tests.txt)).

## Tier 1 kernels and crossover

Tier 1 compares ten million uniformly generated `f64` rows against native loops compiled for the same aarch64 target. The filter rows retain approximately 1%, 50%, or 99% of their inputs, and each interpreter result is checked against its native reference before timing. The NEON intrinsics rows are present only where a distinct hand-written entry exists. The corgi column uses the same input values but runs a different float summation order for `sum` and `dot`, whose bit differences appear in the [raw log](2026-11-02-m5/bench-corgi-tier1.txt).

| Workload | scalar ms | NEON intrinsics ms | native ms | corgi ms |
|---|---:|---:|---:|---:|
| `sum` | 0.791 | - | 0.793 | 5.425 |
| `sum(x * y)` | 1.427 | - | 1.414 | 10.980 |
| `count(x > 0.5)` | 0.841 | - | 0.841 | 1.318 |
| `min` | 4.663 | 0.823 | 0.843 | 1.170 |
| `argmin` | 4.032 | 1.202 | 1.311 | - |
| `filter` 1% | 3.399 | 3.067 | 4.832 | 4.827 |
| `filter` 50% | 3.895 | 3.474 | 4.868 | 5.064 |
| `filter` 99% | 4.212 | 3.969 | 4.917 | 5.178 |

The native and scalar entries for `sum`, `dot`, and `count` are within 1.01x of each other at 10M rows. The NEON entries bring `min` from 5.53x native to 0.98x, and `argmin` from 3.08x to 0.92x. All three filter selectivities are faster than the native compaction loop in this run, with the NEON entry at 0.63x to 0.81x of native. The corgi `argmin` column is absent because that benchmark has no corgi reference for the operation.

The crossover sweep measures the NEON interpreter against native loops at powers of two from 16 to 1,048,576 rows. It uses the same prepared programs for each length, with the native baseline compiled for the aarch64 target. Values below 1.0 mean the interpreter is faster; the table selects representative sizes from the [full sweep](2026-11-02-m5/bench-crossover.txt). Small-array ratios include fixed interpreter dispatch costs and should not be extrapolated to large arrays.

| Rows | `sum` / native | `x * y` / native | `min` / native |
|---:|---:|---:|---:|
| 256 | 12.98 | 6.51 | 5.51 |
| 1,024 | 4.12 | 3.24 | 2.40 |
| 4,096 | 1.76 | 2.30 | 1.26 |
| 8,192 | 1.41 | 1.82 | 1.07 |
| 16,384 | 1.32 | 1.38 | 0.99 |
| 32,768 | 1.09 | 1.37 | 0.94 |
| 1,048,576 | 1.02 | 1.31 | 0.99 |

The first measured lengths at or below 1.5x native are 8,192 for `sum`, 16,384 for `x * y`, and 4,096 for `min`. The sweep does not include the 10M-row steady-state results above. `min` uses the NEON intrinsics entry, while `sum` and `x * y` resolve to the compiler-built scalar entries. The crossovers match the powers of two reported in the older [M5 tier 1 record](2026-10-31-aarch64-kernels.md), but this sweep uses the current revision.

## Tier 2 kernels

The table gives Criterion means in milliseconds at 10 million rows; the native baseline is a plain Rust loop compiled for the same aarch64 target. Inputs are deterministic splitmix64 words, with uniform keys in `0..1024`, random gather indices in `0..10M`, and `scan_by` starts at probability 1/16. A dash means the benchmark has no native reference or a distinct NEON entry. Ratios greater than 1 mean Verkehrt is slower than the native loop.

| Kernel | scalar ms | NEON intrinsics ms | native ms | best / native |
|---|---:|---:|---:|---:|
| `add` i64 | 2.502 | - | 1.910 | 1.31 |
| `scan` add i64 | 3.106 | - | 2.303 | 1.35 |
| `gather` i64 | 26.877 | 26.948 | 22.721 | 1.18 |
| `histogram` | 3.558 | - | 2.522 | 1.41 |
| `reduce_into` add i64 | 4.889 | - | 2.908 | 1.68 |
| `div_const` i64, divisor 60 | 4.160 | - | 1.910 | 2.18 |
| `prev` i64 | 1.754 | - | - | - |
| `and` i64 | 2.544 | - | - | - |
| `xor` i64 | 2.546 | - | - | - |
| `not` i64 | 1.905 | - | - | - |
| `argsort` i64 | 72.662 | - | - | - |
| `scan_by` add i64 | 5.308 | - | - | - |
| `div_const` u64, divisor 60 | 2.886 | - | - | - |

`gather` has no distinct NEON entry and its two timings differ by 0.3%, so the faster scalar result is used for its native ratio. `div_const` i64 has the largest measured native gap at 2.18x, followed by `reduce_into` at 1.68x and `histogram` at 1.41x. The other `argsort` key types measured 72.405 ms (`u64`), 27.584 ms (`i32`), and 7.011 ms (`u8`). Timings alone do not establish which loops the compiler vectorized.

## Grouping

The same benchmark also compares `group_id` against the sort-based grouping idiom at 1 million and 10 million rows. `uniform` draws keys over the full range; `d80k`, `d1m`, `d3m`, and `d10` draw from pools of the indicated sizes. The two-column cases use an additional column derived from the selected pool index, except for `uniform`, whose columns are independently random. All results below are baseline aarch64 Criterion means in milliseconds.

| Rows | Key shape | `group_id` one column | sort one column | `group_id` two columns | sort two columns |
|---|---|---:|---:|---:|---:|
| 1M | uniform | 11.89 | 9.41 | 14.61 | 20.31 |
| 1M | d80k | 3.89 | 14.90 | 5.08 | 20.45 |
| 1M | d1m | 13.13 | 11.36 | 16.41 | 16.58 |
| 1M | d3m | 13.48 | 10.70 | 16.79 | 17.58 |
| 1M | d10 | 0.80 | 15.19 | 1.20 | 20.11 |
| 10M | uniform | 112.32 | 114.37 | 136.68 | 276.85 |
| 10M | d80k | 28.33 | 173.54 | 38.47 | 247.97 |
| 10M | d1m | 65.39 | 164.61 | 88.49 | 238.86 |
| 10M | d3m | 82.94 | 157.75 | 103.79 | 231.35 |
| 10M | d10 | 7.70 | 136.34 | 11.81 | 185.68 |

On one-column uniform keys at 1M rows, the sort idiom is faster: 9.41 ms versus 11.89 ms. At 10M rows, `group_id` is faster for every listed shape, though the one-column uniform case differs by only 2%. For two columns it wins every listed shape, though the 1M d1m case is close at 16.41 versus 16.58 ms. These comparisons use different output group numbering, as the benchmark checks each against its own expected ordering.

## Acceptance queries

The query table reports milliseconds on the prepared 1M-row ClickBench partition and TPC-H scale factor 0.2. Verkehrt's scalar and NEON columns are Criterion means, while corgi and one-thread DuckDB are best-of timings. The two interpreter variants differ on some queries, but this run did not collect per-kernel traces to attribute those differences. Ratios should be computed within each query and host, not against the older x86 table.

ClickBench q03, q08, q15, q19, q30, q31, q32, q40, and q41 are slower than one-thread DuckDB on this machine; q03, q30, q31, q32, and q40 are also slower than corgi. TPC-H q01 runs at 0.67 of one-thread DuckDB and 0.64 of corgi q01, and TPC-H q06 runs at 0.77 of DuckDB but only marginally faster than corgi's printed 1.35 ms. Corgi also has a different TPC-H q01b program, measured at 16.89 ms, which was not used for the q01 comparison. ClickBench q00 is not a comparable SQL benchmark: Verkehrt reads the length of an already-loaded column, while DuckDB runs `COUNT(*)`, and corgi prints its sub-0.01-ms time as `0.00`.

These are single benchmark sessions, not replicated trials across independent builds or thermal states. Corgi's query benchmarks and DuckDB use best-of timings, and small differences between methods or backend variants may be noise. The M5 kernel results do not have a native comparator for every row, and the NEON selection result depends on each query's plan. This record supplies current aarch64 measurements without claiming that the differences from x86 identify an architecture effect.
