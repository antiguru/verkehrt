# Tier 2 kernel and acceptance results (x86)

Extract of the measurement results behind docs/measurements/2026-10-31-tier2.md. All numbers come from the x86 host on 2026-10-31 at commit 428afc9 unless a section names another commit. The commits 0cbd06d and 1132325, which an earlier amend step replaced, ran the same kernels. `git diff 1132325 428afc9` changes one comment and the visibility of one constant in src/kernels/scalar/index.rs, and `git diff 0cbd06d 1132325` changes only src/kernels/tests.rs. Fix round 1 added 11405a6 (AVX-512 `scan_by_add` intrinsics), which changes only `scan_by_add_i64` and `scan_by_add_u64`. No acceptance query uses `scan_by`, so the acceptance numbers stand. The raw logs and the disassembly listings are not part of the repository.

## Host and method

* AMD Ryzen AI MAX+ 395 (Zen 5), AVX2 and AVX-512 F/BW/VL/VBMI2. Boost off, powersave, 3.0 GHz under load (user-reported). Other work shared the host, so each run records its load average.
* Criterion, sample size 10, 0.5 s warm-up, 3 s measurement. Tables give the criterion mean.
* Throughput is input bytes read: 8 bytes per row per array input, 1 byte per bool row. GB/s uses the best auto mean.
* Reference streaming kernel: `tier2/add-i64` best auto (avx2-auto) 9.174 ms for 160 MB, **17.44 GB/s**. Native `add` takes 7.08 ms. The gap between the two is interpreter overhead, mostly the zeroed output buffer (`Array::try_zeroed` writes the 80 MB before the kernel writes it again).

## Finding: whole kernels' auto entries were the scalar entry

At commit 9bb5e11 every `auto` entry of a whole kernel (`gather_<t>`, `histogram`, `reduce_into_<op>_<t>`, `argsort_<t>`) was a 14-byte stub: `push rbx; call <Body as WholeBody>::run; pop; ret`. The callee is the baseline build of the body, so these entries ran the scalar code on every ISA. Run1's auto over scalar ratios near 1.0 for these kernels show that, not a failure of the body to vectorize. Commit 2ffb751 ("Inline the whole kernel bodies into their auto entries") marks the four `run` impls, `checked_keys`, `bucket`, `rows_of`, `Array::try_build`, and `Array::build_bytes` `#[inline(always)]`. After it, the entries are 1.5 to 2.2 KB and contain the ISA's vector code (see the assembly column). `argsort` still calls the out-of-line `ipnsort` from `sort_unstable_by_key`, so its sort stays the baseline build. Only the index initialization loop is compiled for the ISA.

### Casts and `mul` on i64 and u64: which entries emit the AVX-512DQ instructions

The crate's AVX-512 feature string is `avx512f,avx512bw,avx512vl,avx512vbmi2` (src/kernels/x86.rs), without `avx512dq`. `vcvtqq2pd`, `vcvtuqq2pd`, `vcvttpd2qq`, `vcvttpd2uqq`, and `vpmullq` need AVX-512DQ, so the `auto` entries cannot emit them. The check ran on commit 3a60e54 (the head before the fix commits, with no kernel change since 428afc9): `cargo bench --no-run --bench tier1`, then `objdump -d --no-show-raw-insn -C` of the bench binary, and a search of the symbols `verkehrt::kernels::x86::auto::{avx2,avx512}::elementwise::<Unary<S, D, CastOp, false>>` and `<Binary<i64, i64, MulOp, false>>`. No entry contains `vcvtqq2pd`, `vcvtuqq2pd`, `vcvttpd2qq`, `vcvttpd2uqq`, or `vpmullq`.

| Kernel | AVX2 hot loop | AVX-512 hot loop | Verdict |
|---|---|---|---|
| cast_i64_f64 | 8 scalar `vcvtsi2sdq` per iteration, packed with `vunpcklpd` and `vinsertf128`, stored as `ymm` | 8 scalar `vcvtsi2sdq` per iteration, packed with `vinsertf128` and `vinsertf64x4`, stored as `zmm` | Scalar conversions on both ISAs, only the stores are vector. Strain case |
| cast_f64_i64 | scalar `vcvttsd2si` per row plus `vucomisd` compares for the saturation and NaN fixups, assembled into `ymm` stores | scalar `vcvttsd2si` per row plus `vucomisd`, assembled into `zmm` stores | Scalar on both ISAs. Strain case |
| cast_f64_u64 | scalar `vcvttsd2si` with `vsubsd` for the top half, `vucomisd` fixups | scalar `vcvttsd2usi` (AVX-512F, scalar form) per row plus `vucomisd` fixups | Scalar on both ISAs. Strain case |
| cast_u64_f64 | `ymm`, 16 rows per iteration: `vpblendd` and `vpor` with magic constants, `vpsrlq`, `vsubpd`, `vaddpd` | `zmm`, 32 rows per iteration: `vpternlogq`, `vpsrlq`, `vporq`, `vsubpd`, `vaddpd` | Vectorized on both ISAs by the magic-constant split, no DQ instruction |
| mul_i64 | `ymm` `vpmuludq` emulation: three `vpmuludq` plus `vpsllq`, `vpsrlq`, `vpaddq` per vector | `zmm` `vpmuludq` emulation of the same shape | Vectorized on both ISAs, by the emulation, not by `vpmullq` |

The `imul` and scalar conversion instructions that also appear in the `cast_u64_f64` and `mul_i64` symbols sit outside the vector loops, in the scalar paths for short inputs and leftover rows. The casts were not timed.

Timing and assembly disagree in two places, and the assembly decides. First, histogram and reduce_into time at 0.79 and 0.85 of scalar, but the hot bucket loop is scalar: the gain is the bounds pass moving from SSE2 to `ymm`/`zmm`. Second, div_const_u64 times at 1.06 of scalar although its auto loop is partially vectorized: the baseline build already uses SSE2 `psrlq` for the uniform shifts and scalar `mul` for the multiply-high, so both builds are the same shape.

## Intrinsics decisions

Priority by acceptance queries: histogram, reduce_into, div_const, then gather and scan.

### histogram and reduce_into: not committed, strain case

The bucket loop did not vectorize. The spec names `vpconflictq` or replicated sub-histograms on AVX-512. Both were prototyped in a standalone crate with the kernel's clamp and bounds semantics, best-of timing, at 14:20 to 14:23, load 1.6 to 4.0. Variants: A the current two-pass shape (bounds pass, then scalar loop), B one fused pass (clamp and accumulate the bad flag), C fused with 4 scalar sub-histograms, D AVX-512 `vpconflictq` (vectors without duplicates do gather, add, scatter, others fall back to scalar), E AVX-512 gather and scatter on 8 replicated sub-histograms, lane `j` owning copy `j`.

| Case | A base | A avx512 | B fused | C 4 sub | D vpconflictq | E 8 sub gather/scatter |
|---|---|---|---|---|---|---|
| histogram, 10M keys in 0..1024 | 5.56 | 5.31 to 6.45 | 4.82 to 7.07 | 5.50 to 7.18 | 10.13 | 9.62 to 9.73 |
| histogram, 1.2M rows, 4 keys of 65536 (TPC-H q01 shape) | 1.16 | 0.93 | 0.98 | 0.98 | 0.87 | 1.49 |
| histogram, 1.2M rows, runs of 600 (q42 shape) | 0.89 | 0.67 | 0.86 | 0.84 | 0.54 | 1.33 |
| reduce_into add, 10M rows in 0..1024 | 7.32 | 6.11 to 6.92 | 5.52 (base) | - | - | 9.81 to 9.83 |
| reduce_into add, 4 keys of 65536 | - | 0.95 | 1.01 | - | - | 1.55 to 1.61 |
| reduce_into add, runs of 600 | - | 0.72 | 0.94 | - | - | 1.33 to 1.34 |

Ranges are repeated runs of rebuilt binaries. E loses to the scalar loop by 1.5x to 1.9x in every case, and D by 1.6x to 1.9x on the bench's uniform keys. Scatter is slow on this core, and Zen 5 handles repeated increments of one address well, so the scalar loop is not latency-bound even with 4 keys. D needs AVX512CD, which `Isa::Avx512` does not check. Decision: no intrinsics. The measurement document records histogram and reduce_into as scalar bucket loops on AVX2 and AVX-512 (bucketed reductions, already a strain case in the spec), with a vectorized bounds pass.

D is the fastest variant on the two skewed shapes (0.87 and 0.54 ms), and fusion alone does not explain it. B is also a single fused pass with a scalar bucket loop, yet it measures 0.98 and 0.86 ms on the same shapes. On the runs-of-600 shape nearly every 8-key vector holds a duplicate, so D increments almost all keys through its scalar fallback, the same increments B makes. What D does differently is its bounds handling: it tests eight keys per `vpcmpuq` into a mask and runs the conflict test and the fallback per 8-key chunk, while B ORs a flag per key inside the increment loop. The prototype did not isolate which of these differences gives D its 0.54 against B's 0.86 ms. B's own uniform-key time varies from 4.82 to 7.07 ms across rebuilds, so codegen layout also moves these numbers.

Gap over 1.5x of native: histogram 1.72x, reduce_into 1.94x. The native loop is one pass that relies on Rust's bounds-checked indexing. The kernel reads the keys twice, once for the order-independent error check and once for the buckets. Fusing the check into the bucket loop (variant B: clamp, OR the out-of-range flag, report the first bad key only on the error path) gave 13% (histogram) and 25% (reduce_into) in the prototype, keeps the error independent of row order, and applies to the scalar and auto entries alike. Candidate for plan 5, not done here.

### div_const_i64 and div_const_u64: strain case, no intrinsics

Neither AVX2 nor AVX-512 has a 64-bit multiply-high, and the assembly shows the compiler extracting each lane to a scalar `mul`. The rest of the computation is vector code, so the i64 auto entry runs at 0.65 of scalar and 0.85 of the native `x / 60` loop, which is all scalar. The u64 entry runs at the scalar entry's speed (1.06) because the baseline build has the same shape. The spec names no technique. The measurement document records both as strain cases like `mul_i64`: multiply-high scalar on both ISAs. A `vpmuludq`-based 64-bit multiply-high emulation was not attempted.

### gather_i64, gather_u64, gather_f64: intrinsics committed

The auto row loop is scalar. The entries `gather::avx2` and `gather::avx512` in `src/kernels/x86/gather.rs` reuse the scalar body's `Gather::checked` (argument and bounds check), then load rows with `vpgatherqq` (`_mm256_i64gather_epi64` / `_mm512_i64gather_epi64`). One entry per ISA serves all 64-bit row types, since a gather moves bits. Final run: avx2-intrinsics 39.34 ms, avx512-intrinsics 40.57 ms against scalar 49.02 ms, **0.80 and 0.83 of scalar**, and 1.01 and 1.04 of the best native (native-avx2 `vpgatherqq` loop, 39.09 ms). Run3 gave 39.90 and 40.74 ms against scalar 50.84 ms (0.78 and 0.80). Prototype (best-of, into a preallocated buffer): source 10M, ymm 36.2 and zmm 37.3 ms against scalar 42.1 (base) and 45.2 (avx512 build). For a 1024-row source zmm wins 8% (6.41 against 6.99 ms). The 10M bench decides. Known cost of the entry: for a 65536-row (512 KB) source the hardware gather is slower than the scalar loop, ymm 9.85 and zmm 11.03 ms against the scalar avx512 build's 9.34 ms, 1.05x and 1.18x. The entry is installed for every source size, so the intrinsics backend pays this on mid-sized sources. TPC-H q01's `gather(counts, groups)` has a 65536-row source, but its index array holds only the few non-empty groups, so the cost there is negligible. `tests/isa_variants.rs` now checks 39 AVX2 and 41 AVX-512 intrinsics kernels (3 more each), and `variant_entry_counts_are_stable` records the counts. 32-bit, `u8`, and bool gathers keep the auto entry.

### scan_add_i64: not committed, strain case

The auto loop is the scalar `add` chain on both ISAs. The spec's technique, a log-step in-register prefix plus carry, was prototyped on AVX-512 (`valignq` shifts by 1, 2, 4, add carry, `vpermq` broadcast of lane 7): 4.04 ms against the scalar loop's 4.17 ms at 10M rows into a preallocated buffer, 3%. The scan is memory-bound at this size (the interpreter's 7.4 ms includes allocation and zeroing of the 80 MB output). A 3% prototype gain is inside the run-to-run noise of the interpreter bench (scan scalar 7.14 to 7.40 ms across runs), so it cannot be shown to beat the scalar entry. Decision: no intrinsics. The measurement document records `scan_<op>` on integers as a scalar loop on AVX2 and AVX-512.

### scan_by_add_i64 and scan_by_add_u64: AVX-512 intrinsics committed, AVX2 strain case

`scan_by` is not memory-bound like `scan`: 10.80 ms against scan's 7.37 ms, 0.48 of add_i64's bandwidth against 0.62. The auto hot loop is branch-free (`cmovne` resets the accumulator at a start), so the cost is not branch misses. It is the two-instruction dependency per row (`cmov`, then `add`) against one `add` for `scan`. The segmented log-step was prototyped at 10M rows into preallocated buffers (best-of, load 7.0):

| Starts probability | scalar base | scalar avx512 build | log-step AVX2 | log-step AVX-512 |
|---|---|---|---|---|
| 1/16 | 7.01 | 6.98 | 7.10 | 4.99 |
| 1/2 | 7.02 | 6.96 | 7.12 | 4.75 |
| 1/1024 | 7.01 | 6.97 | 7.13 | 4.88 |

AVX-512 keeps the start flags in a mask register and shifts lanes with `valignq` against zero, so each step is one shift and one masked add. AVX2 needs `vpermq` plus a blend for a one-lane shift and `vperm2i128` for a two-lane shift, with the flags as vectors, and it runs at the scalar loop's speed. Decision: the AVX-512 entry `scan::update_avx512` in `src/kernels/x86/scan.rs` serves `scan_by_add_i64` and `scan_by_add_u64` (commit 11405a6). It parses the tile with the scalar body's `tile_rows`, so it fails exactly when the scalar entry fails, and it carries the accumulator across tiles. In the interpreter bench (fix 1 run, same run): avx512-intrinsics 8.38 ms against scalar 10.34 ms, avx2-auto 10.35 ms, avx512-auto 10.49 ms, **0.81 of scalar**. `tests/isa_variants.rs` checks it, including tiled runs, and now counts 43 AVX-512 intrinsics kernels. The measurement document records `scan_by_add` as a scalar loop on AVX2 and other `scan_by` folds as scalar loops on both ISAs. The other folds were not prototyped: integer `min`, `max`, and the bitwise folds have the same select-plus-op chain and could take the same segmented form.

### prev, bitwise, argsort

* `prev`: a `memcpy`, already vectorized by libc. No decision needed.
* `and`, `or`, `xor`, `not`: vectorized (`ymm` 16 rows, `zmm` 32 rows per iteration), memory-bound at add_i64's bandwidth.
* `argsort`: the sort is the baseline build of `sort_unstable_by_key` on all ISAs, the scalar argsort strain case the spec already lists. 0.10 GB/s.

### Not attempted

* `vpconflictq` reduce_into (histogram's D already loses on uniform keys).
* div_const multiply-high emulation with `vpmuludq` (spec names no technique).
* Segmented log-step for the other `scan_by` folds (min, max, mul, bitwise), and for `scan_by` on 32-bit and 8-bit inputs.
* Gathers on 32-bit, `u8`, and bool rows.
