# Fast argsort: measurements

This document records how plan 5 chose the new `argsort` algorithm and what it gains over the plan 4 comparison sort.
Plan 4 sorted row positions with `sort_unstable_by_key` and a position tiebreak, which took about 750 ms per 10M `i64` rows on every variant.
The candidates from the plan 5 spec were prototyped on plain slices at 1M and 10M rows, and the winner, an LSD radix sort with byte digits, replaced the kernel body.
A second round settled the position width and the small-input switch point.
The last sections give the per-variant times of the final kernel and its memory cost.

| Item | Value |
|---|---|
| CPU | AMD Ryzen AI MAX+ 395 (Zen 5, 32 logical CPUs) |
| Frequency scaling | boost off, governor `powersave`, 3.0 GHz under load (user-reported, not recorded during the runs) |
| Kernel, rustc | 7.2.11+deb14-amd64, 1.99.0 |
| Profile | release (LTO, `codegen-units = 4`), `CARGO_INCREMENTAL=0` |
| Input | `splitmix` rows of `benches/tier1.rs` (seed 1), uniform over the full `i64` range. The `u64`, `i32`, and `u8` rows are the same values reinterpreted or truncated. |

Kernel times come from criterion with `sample_size(10)`, a 0.5 s warm-up, and a 3 s measurement time (`tier2/argsort-*` in `benches/tier1.rs`), timing `Prepared::execute`, so they include the output allocation.
Prototype times come from a throwaway criterion bench with the same settings at 10M rows and a 1 s measurement time at 1M rows, calling each candidate on a slice and returning a fresh `Vec<i64>`.
The tables give the criterion mean.
Every raw file starts with the load average before the run and ends with the one after it, which ranged from 2.0 to 7.4.
Differences within about 10% are noise on this host.

## Candidates

* `plan4`: the plan 4 body, `sort_unstable_by_key` over positions with key `(xs[i], i)`, which loads each key indirectly.
* `gather-unstable`: (key, `u32` position) pairs gathered into a contiguous buffer and sorted with `sort_unstable`. The pairs are distinct, so the result is stable.
* `gather-stable`: the same pairs sorted with the stable `sort_by_key` on the key alone (`i64` only).
* `packed-unstable`: for `i32` and `u8`, the key image and a 32-bit position packed into one `u64` word, sorted with `sort_unstable`.
* `lsd8` and `lsd11`: LSD radix sort on interleaved (key image, `u32` position) pairs with 8-bit and 11-bit digits. One counting pass builds every digit's histogram, a pass whose digit is equal in every row is skipped, the first pass reads the input, and the last writes the positions to the output.
* `lsd8-split`: `lsd8` with separate key and position arrays.
* `lsd8-unchecked` and `lsd11-unchecked`: the same with unchecked stores in the scatter, to price the bounds checks.

The key image flips the sign bit of signed keys, so unsigned order of the image is signed order of the key.

## Round 1: candidates at 1M and 10M rows

Times in ms, baseline target (no target features), from `proto-round1-1M.txt`, `proto-round1-10M-i64-u64.txt`, and `proto-round1-10M-i32-u8.txt`.

| Candidate | `i64` 1M | `i64` 10M | `u64` 1M | `u64` 10M | `i32` 1M | `i32` 10M | `u8` 1M | `u8` 10M |
|---|---|---|---|---|---|---|---|---|
| `plan4` | 41.6 | 746.8 | 40.9 | 749.9 | 40.0 | 643.7 | 36.9 | 432.2 |
| `gather-unstable` | 30.7 | 347.9 | 30.8 | 348.6 | 25.0 | 284.3 | 24.7 | 279.4 |
| `gather-stable` | 33.2 | 414.0 | | | | | | |
| `packed-unstable` | | | | | 15.0 | 172.5 | 15.1 | 173.1 |
| `lsd8` | 13.5 | 144.2 | 13.2 | 142.3 | 5.15 | 60.3 | 1.15 | 13.3 |
| `lsd8-unchecked` | 12.9 | 142.2 | | | 4.79 | 57.2 | 1.14 | 13.2 |
| `lsd11` | 15.5 | 197.8 | 15.5 | 193.6 | 4.67 | 109.2 | | |
| `lsd11-unchecked` | 15.2 | 203.9 | | | | | | |
| `lsd8-split` | 17.0 | 155.3 | | | 6.98 | 79.6 | | |

`lsd8` is the fastest checked candidate on every type at 10M rows, 5.2x `plan4` on 64-bit keys, 10.7x on `i32`, and 32x on `u8`.
At 1M rows it is 3.1x `plan4` on 64-bit keys, 7.8x on `i32`, and 32x on `u8`.
`lsd11` loses at 10M rows on every type, by 1.4x on 64-bit keys and 1.8x on `i32`, and wins only on `i32` at 1M rows, by 9%, which is within noise.
Interleaved pairs and separate arrays tie on `i64` at 10M rows (144.2 against 155.3 ms, 7.7%, inside the noise band), and interleaved pairs win by 32% on `i32`.
Unchecked stores change the time by -3% to +7%, within noise (`lsd11-unchecked` at 10M rows was 3% slower, 203.9 against 197.8 ms), so the kernel keeps the bounds checks and adds no `unsafe`.

## Round 2: position width and small inputs

Positions are `u32` whenever the input has at most `u32::MAX` rows, and `u64` above that.
Times in ms from `proto-round2-poswidth.txt`, which ran at load 6.4 to 6.5.

| Candidate | `i64` 1M | `i64` 10M | `i32` 1M | `i32` 10M |
|---|---|---|---|---|
| `lsd8`, `u32` positions | 13.6 | 146.1 | 5.30 | 62.2 |
| `lsd8`, `u64` positions | 15.7 | 156.8 | 7.67 | 75.5 |

`u32` positions halve the pair of an `i32` key, from 16 to 8 bytes, and gain 18% to 31% on `i32`.
On `i64` the pair is 16 bytes either way, because of alignment, and the gain is 7% to 13%.

The radix sort pays a fixed cost for zeroing and scanning its histograms, so short inputs use the comparison sort of plan 4.
Times in µs from `proto-round2-small.txt`, which ran at load 2.2 to 7.4.

| Rows | `i64` `plan4` | `i64` `lsd8` | `i32` `plan4` | `i32` `lsd8` | `u8` `plan4` | `u8` `lsd8` |
|---|---|---|---|---|---|---|
| 2 | 0.022 | 1.84 | 0.021 | 0.917 | 0.021 | 0.241 |
| 8 | 0.035 | 1.94 | 0.037 | 0.962 | 0.037 | 0.236 |
| 32 | 0.234 | 2.17 | 0.232 | 1.12 | 0.224 | 0.283 |
| 128 | 1.16 | 3.27 | 1.08 | 1.56 | 1.10 | 0.391 |
| 512 | 5.38 | 7.34 | 5.43 | 3.53 | 5.35 | 0.858 |
| 2048 | 26.3 | 24.0 | 26.2 | 11.0 | 26.4 | 2.53 |
| 8192 | 124.9 | 90.3 | 120.0 | 41.6 | 122.7 | 9.16 |
| 32768 | 961.5 | 385.7 | 951.0 | 165.9 | 934.9 | 37.5 |

The crossover lies between 512 and 2048 rows for 64-bit keys, between 128 and 512 for `i32`, and between 32 and 128 for `u8`.
The kernel switches to the radix sort above 1024 rows for 64-bit keys, above 256 for `i32`, and above 32 for `u8`.
Near each switch point the two methods differ by a few microseconds, a figure interpolated from the bracketing sizes in the table, since the switch points themselves were not measured.

## Choice

The kernel is `lsd8` with `u32` positions where they fit, and the plan 4 comparison sort at or below the switch points above (`src/kernels/scalar/index/radix.rs`).
It won every 10M-row comparison and every 1M-row comparison except `i32` against `lsd11`, which is within noise.
An LSD radix sort with a forward scatter is stable, so its output is the plan 4 output on every input.
The scratch buffers are reserved with `try_reserve_exact`, and a failed reservation is an error of the kernel call.

The layout trades memory for time only weakly, so the decision rests on the `i32` result.
Separate key and position arrays need 24 bytes of scratch per row for 64-bit keys (two 8-byte key arrays and two 4-byte position arrays), 25% less than the 32 bytes of interleaved pairs, and they tie on time for `i64`.
On `i32` they lose by 32%, so one interleaved layout serves every type, while the split layout would win memory on 64-bit keys only.
Narrowing the 64-bit pairs to 8 bytes (high key half and position) after the four low passes would cut the traffic of the last four passes, but it was not measured, so it stays a candidate.
`gather-unstable` needs a single 16-byte buffer per row for 64-bit keys, half the radix scratch, but runs about 2.4x slower than `lsd8` (347.9 against 144.2 ms on `i64`).
The kernel keeps interleaved pairs for now. If memory matters on a host, the split layout for 64-bit keys or narrowing are the lower-memory options, at no measured time cost for the split layout.

## Final kernel: per-variant times

Times in ms at 10M rows, from `baseline-plan4-*.txt` (load 2.0 to 2.2) and `final-*.txt` (load 2.6 to 2.9).
Speedup is plan 4 over final on the same variant.

| Type | Variant | Plan 4 | Final | Speedup |
|---|---|---|---|---|
| `i64` | scalar | 746.3 | 149.2 | 5.0x |
| `i64` | `x86-64-v3-auto` | 743.9 | 149.6 | 5.0x |
| `i64` | `x86-64-v4-auto` | 747.3 | 150.1 | 5.0x |
| `u64` | scalar | 749.0 | 164.0 | 4.6x |
| `u64` | `x86-64-v3-auto` | 752.9 | 164.9 | 4.6x |
| `u64` | `x86-64-v4-auto` | 754.6 | 149.5 | 5.0x |
| `i32` | scalar | 649.5 | 62.4 | 10.4x |
| `i32` | `x86-64-v3-auto` | 647.8 | 62.9 | 10.3x |
| `i32` | `x86-64-v4-auto` | 646.9 | 62.6 | 10.3x |
| `u8` | scalar | 434.8 | 14.0 | 31x |
| `u8` | `x86-64-v3-auto` | 436.1 | 13.9 | 31x |
| `u8` | `x86-64-v4-auto` | 437.4 | 14.0 | 31x |

The 64-bit times fall into two levels, about 149 ms and about 164 ms, which move between variants from run to run.
In `impl1-i64-u64.txt`, the same algorithm before a refactor that moved the prefix sums into the scatter, `i64` `x86-64-v3-auto` took 165 ms and `u64` scalar 150 ms.
The 10% step is therefore noise of the host, not a property of a variant.
The `auto` entries run within noise of scalar on every type, so compiling the passes under the level's features does not help, and the kernel has no intrinsics.
`argsort` stays a strain case, a scalar loop on a supported ISA.

After the review, the `u32` position conversion became `u32::try_from` with a debug assertion (`fix1-i64-i32.txt`, `fix1-i64-i32-rerun.txt`, load 2.0 to 2.7).
`i64` stayed on the same two levels (150.8 to 166.3 ms).
`i32` took 64.9 to 67.2 ms against 62.4 to 62.9 ms before, 4% to 8% slower, and the slowdown appeared in both runs.
Criterion flagged 3 of the 4 `i32` rows as regressed. The fourth, the rerun of `i32` scalar, reported no change because criterion compared it with the first `fix1` run, which was already slow.
The before and after runs were not paired, so the size is uncertain, but a real cost of about 5% is plausible.
The kernel keeps the checked `u32::try_from` form, which favors correctness over those few percent.

## Memory

Peak extra memory beyond the input and the `i64` output is two scratch buffers of (key image, position) pairs, allocated only when more than one pass runs.
The second buffer is needed only when three or more passes run.

| Type | Pair size | Peak scratch per row | At 10M rows |
|---|---|---|---|
| `i64`, `u64` | 16 bytes | 32 bytes | 320 MB |
| `i32` | 8 bytes | 16 bytes | 160 MB |
| `u8` | none | 0 bytes, a single pass reads the input and writes the output | 0 |

Above `u32::MAX` rows the positions are `u64`, and `i32` pairs grow to 16 bytes, or 32 bytes of scratch per row.
The histograms are a fixed 16 KB on the stack, and the comparison path needs nothing beyond the output.
Plan 4 needed no scratch, so the speedup costs up to four times the output size in transient memory on 64-bit keys.
The section on the choice weighs this cost against the split layout (24 bytes per row) and `gather-unstable` (16 bytes per row).
