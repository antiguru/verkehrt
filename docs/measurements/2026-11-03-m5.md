# Kernels and acceptance queries on M5 Max: November 3 measurements

This record measures commit `ab0c3cf` on an Apple M5 Max, after selective predicate evaluation and tiled reduction fusion merged. It covers tier 1 and tier 2 kernels at 10 million rows, the dispatch crossover sweep, grouping at 1 and 10 million rows, all 20 ClickBench acceptance programs, and both TPC-H acceptance programs. Verkehrt and corgi were rerun on the same machine and prepared data; the one-thread DuckDB timings were reused from the earlier [M5 record](2026-11-02-m5.md), not rerun. The [x86 measurements](2026-10-31-tier2.md) use a different host and earlier code, so their absolute times are not directly comparable.

## Setup and method

|---|---|
| CPU, OS | Apple M5 Max, arm64, Darwin 27.2.0 |
| Power | AC during measurement; battery charging at end of session |
| Revision, compiler | `ab0c3cf8d5d5e0f0faa30f665e68145495c4e95f`, rustc 1.99.1 |
| Build | Release profile with LTO, `CARGO_INCREMENTAL=0`, `--locked` for Verkehrt |

| DuckDB reference | 1.5.6, `SET threads = 1`, previously recorded on this M5 and prepared data |
| ClickBench | `hits_0.parquet`, 1,000,000 rows, prepared by `scripts/prepare-acceptance.sh` |
| TPC-H | Scale factor 0.2, prepared by the same script |

Verkehrt's numbers are Criterion means with 10 samples, a 0.5-second warm-up, and a 3-second measurement period per variant, except for the crossover sweep, which uses 20 samples, a 0.1-second warm-up, and a 0.3-second measurement period. Kernel and query timers cover `Prepared::execute`, excluding parsing, planning, and input loading; kernel outputs are checked against references before timing. The `scalar` label means the baseline aarch64 build, which the compiler may vectorize with NEON; `neon-intrinsics` uses hand-written entries where available and otherwise falls back to those scalar entries. Corgi reports best-of query timings and DuckDB reports best-of repeated one-thread timings, both more favorable statistics than Criterion means.

Raw results are in [tier 1](2026-11-03-m5/bench-tier1.txt), [crossover](2026-11-03-m5/bench-crossover.txt), [corgi tier 1](2026-11-03-m5/bench-corgi-tier1.txt), [tier 2](2026-11-03-m5/bench-tier2.txt), [ClickBench](2026-11-03-m5/bench-clickbench.txt), [TPC-H](2026-11-03-m5/bench-tpch.txt), [corgi ClickBench](2026-11-03-m5/corgi-clickbench.txt), and [corgi TPC-H](2026-11-03-m5/corgi-tpch.txt). Verkehrt used `cargo bench --locked --bench tier1 -- 'tier1/' --noplot`, then `'crossover/'` and `'tier2/'`, and `cargo bench --locked --bench acceptance -- 'acceptance/SUITE/' --noplot`, with the matching `VERKEHRT_CLICKBENCH` or `VERKEHRT_TPCH` directory set. Corgi's `clickbench` and `tpch` benches used the same directories via `CORGI_CLICKBENCH` and `CORGI_TPCH`; the DuckDB timings come from saved TSV files in those directories. Release-mode tests with both datasets set ran 377 tests, all passing, with one skipped by nextest, including checks against saved DuckDB answers ([test log](2026-11-03-m5/tests.txt)); [host details](2026-11-03-m5/host-after.txt) record AC power at the end of the session.

## Tier 1 kernels and crossover

Tier 1 compares ten million deterministic `f64` rows against native loops compiled for the same aarch64 target. Filter rows retain approximately 1%, 50%, or 99% of their inputs, and each interpreter result is checked against its native reference before timing. The NEON column appears only where a distinct hand-written entry exists. Corgi uses the same input values but a different float summation order for `sum` and `dot`, whose bit differences appear in the [raw log](2026-11-03-m5/bench-corgi-tier1.txt).

| Workload | scalar ms | NEON intrinsics ms | native ms | corgi ms |
|---|---:|---:|---:|---:|
| `sum` | 0.891 | - | 0.883 | 5.522 |
| `sum(x * y)` | 1.458 | - | 1.427 | 11.145 |
| `count(x > 0.5)` | 0.897 | - | 0.894 | 1.425 |
| `min` | 4.783 | 0.890 | 0.934 | 1.204 |
| `argmin` | 3.676 | 1.226 | 1.308 | - |
| `filter` 1% | 3.476 | 3.109 | 2.844 | 5.109 |
| `filter` 50% | 4.032 | 3.514 | 2.812 | 5.198 |
| `filter` 99% | 4.351 | 4.025 | 2.862 | 5.344 |

The baseline entries for `sum`, `dot`, and `count` run at 1.01x, 1.02x, and 1.00x native, respectively. NEON brings `min` from 5.12x to 0.95x native and `argmin` from 2.81x to 0.94x. NEON `filter` runs at 1.09x, 1.25x, and 1.41x native as selectivity rises. Unlike the [previous revision](2026-11-02-m5.md), these filters do not beat the native loop: the native reference became roughly 42% faster between builds despite unchanged benchmark source, and a [separate rerun](2026-11-03-m5/bench-filter-rerun.txt) reproduced the new baseline. This cross-build drift is unexplained, so the filter ratio difference is not evidence that either merged feature slowed filtering.

The crossover sweep measures the interpreter against native loops at powers of two from 16 to 1,048,576 rows. The first measured lengths at or below 1.5x native are 8,192 for `sum`, 16,384 for `x * y`, and 4,096 for `min`, according to the [full sweep](2026-11-03-m5/bench-crossover.txt). `min` uses the NEON intrinsics entry, while `sum` and `x * y` use compiler-built baseline entries. Small-array ratios include fixed interpreter dispatch costs and should not be extrapolated to the 10M-row measurements above.

## Tier 2 kernels

These Criterion means measure 10 million rows against native loops compiled for the same aarch64 target where such a reference exists. Inputs are deterministic splitmix64 words, with uniform keys in `0..1024`, random gather indices in `0..10M`, and `scan_by` starts at probability 1/16. A dash means no native reference or distinct NEON entry exists. Ratios above 1 mean the interpreter is slower than native.

| Kernel | scalar ms | NEON intrinsics ms | native ms | best / native |
|---|---:|---:|---:|---:|
| `add` i64 | 2.555 | - | 1.937 | 1.32 |
| `scan` add i64 | 3.104 | - | 2.352 | 1.32 |
| `gather` i64 | 28.926 | 28.758 | 24.193 | 1.19 |
| `histogram` | 3.651 | - | 2.529 | 1.44 |
| `reduce_into` add i64 | 4.981 | - | 3.365 | 1.48 |
| `div_const` i64, divisor 60 | 4.250 | - | 2.009 | 2.12 |
| `prev` i64 | 1.777 | - | - | - |
| `and` i64 | 2.548 | - | - | - |
| `xor` i64 | 2.546 | - | - | - |
| `not` i64 | 1.914 | - | - | - |
| `argsort` i64 | 72.940 | - | - | - |
| `scan_by` add i64 | 5.316 | - | - | - |
| `div_const` u64, divisor 60 | 2.897 | - | - | - |

`gather` has no distinct NEON entry, so its 28.758 ms NEON-labeled timing is a fallback to the scalar kernel. `div_const` i64 has the largest native gap in this table at 2.12x, followed by `reduce_into` at 1.48x and `histogram` at 1.44x. The other `argsort` key types measured 72.944 ms (`u64`), 27.715 ms (`i32`), and 7.016 ms (`u8`). Timings alone do not establish which loops the compiler vectorized.

## Grouping

The tier 2 benchmark compares `group_id` with the sort-based grouping idiom at 1 million and 10 million rows. `uniform` draws full-range keys, while `d80k`, `d1m`, `d3m`, and `d10` draw from pools of the indicated sizes. Two-column cases use an additional column derived from the selected pool index, except for `uniform`, whose columns are independently random. The results are baseline aarch64 Criterion means in milliseconds.

| Rows | Key shape | `group_id` one column | sort one column | `group_id` two columns | sort two columns |
|---|---|---:|---:|---:|---:|
| 1M | uniform | 12.28 | 9.44 | 14.87 | 20.48 |
| 1M | d80k | 3.93 | 15.90 | 4.95 | 21.02 |
| 1M | d1m | 13.69 | 11.46 | 16.48 | 16.76 |
| 1M | d3m | 14.07 | 10.96 | 17.34 | 16.30 |
| 1M | d10 | 0.81 | 15.38 | 1.15 | 20.42 |
| 10M | uniform | 114.54 | 114.80 | 141.70 | 283.70 |
| 10M | d80k | 28.73 | 178.04 | 37.51 | 254.02 |
| 10M | d1m | 66.48 | 168.85 | 88.67 | 243.39 |
| 10M | d3m | 82.89 | 159.73 | 105.39 | 237.13 |
| 10M | d10 | 7.85 | 141.04 | 11.53 | 188.49 |

At 1M rows, one-column `uniform`, `d1m`, and `d3m` favor sorting; two-column `d3m` also favors sorting. At 10M rows, `group_id` is faster for every measured shape, though the one-column uniform times differ by less than 1%. Group numbering differs between the methods, so the benchmark checks each against its own expected ordering. These observations apply to the measured key distributions rather than all grouping inputs.

## Same-build feature comparisons

Separate adjacent runs on the same `ab0c3cf` build disable and enable selective predicate evaluation for q40 through q42 using `VERKEHRT_SELECTIVE=off` and the default. Each entry below is the Criterion mean in milliseconds, with disabled before enabled, rather than a comparison against the full-suite query table above. The [disabled](2026-11-03-m5/bench-selective-off.txt) and [enabled](2026-11-03-m5/bench-selective-on.txt) logs preserve the full estimates. These paired runs limit cross-build confounding but remain one pair per setting, not replicated experiments.

| ClickBench query | scalar off → on ms | NEON off → on ms |
|---|---:|---:|
| q40 | 2.699 → 2.355 | 2.509 → 2.137 |
| q41 | 2.068 → 1.768 | 1.877 → 1.558 |
| q42 | 1.563 → 1.331 | 1.469 → 1.273 |

A second adjacent pair disables and enables tiled reduction fusion for q03 using `VERKEHRT_REDUCTION_FUSION=off` and the default. Scalar measured 1.036 → 0.944 ms, and NEON measured 1.165 → 0.943 ms in the [disabled](2026-11-03-m5/bench-fusion-off.txt) and [enabled](2026-11-03-m5/bench-fusion-on.txt) logs. These runs support a gain on this host without proving the size of the gain across repeated sessions. In particular, the full-suite q03 and q40–q42 results differ from their later enabled measurements, so pair adjacent runs when interpreting each switch rather than mixing runs.

These are single sessions with load and thermal variation, not independent replicated trials. Corgi and DuckDB use best-of timings against Verkehrt's means, and the DuckDB reference predates the new interpreter build. The filter native baseline drift shows that even unchanged benchmark code can move substantially between builds on this host. This record describes measured outcomes, not architecture-only speedups or a causal explanation for cross-build changes.
